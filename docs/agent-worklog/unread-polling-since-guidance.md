# Unread Polling — Document the `since` Cursor Requirement

## Changes
- `server.py` `INSTRUCTIONS` (served at `GET /api/v1/instructions`): the "Status (long-polling)" and "Behavior" sections now state explicitly that `/api/v1/me/unread` has no server-side read-tracking, that omitting `since` re-scans a rolling 10-minute window on every call, and that callers must advance `since` to the newest `created_at` they've seen.
- `launch.sh` `build_prompt()` step 2a: the example `curl` for the poll loop now includes `since=<newest_created_at_seen>` and a note telling the spawned agent to track and advance it.

## Decisions
- No code/behavior change to `/api/v1/me/unread` itself — this was a documentation-only fix. Investigation confirmed the server has no read/unread state at all (no `read_at`/`last_read_message_id`/cursor anywhere in the schema); "unread" is entirely re-derived per call from the caller-supplied `since` (default: `now - 10min`), scoped to the agent's room + DMs, excluding the agent's own messages. Polling, long-polling, or replying never marks anything read.
- Root cause of the reported symptom (agents repeatedly seeing the same already-answered message): both `launch.sh:265`'s example loop and the in-product `INSTRUCTIONS` text told agents to call `GET /api/v1/me/unread?wait=60` in a loop without ever mentioning `since` needs to advance. Any agent following the docs literally gets every not-self-authored message from the last 10 minutes on *every* poll — duplicate delivery is the designed behavior of that loop, not an edge case.
- Considered adding server-side dedup (e.g. persisting a per-agent cursor) instead of a docs fix. Rejected for this change: the API already supports correct dedup via `since` (verified via `tests/test_api.py::TestUnread` and the `since` filter tests) — the only actual defect was that the two places instructing agents how to poll never demonstrated the required pattern. Adding server-side state would be a larger, unrequested design change to a project whose schema deliberately keeps `agents.room_id` as the only membership state (see `docs/agent-worklog/room-membership-and-token-naming.md`).

## Testing
- `make test-api test-integration` (66 tests) passes unchanged — no runtime behavior was touched, only doc strings.
- `tests/test_api.py::TestInstructions::test_instructions_returns_markdown_with_base_url` (only test asserting on `INSTRUCTIONS` content) passes; it checks for `"chait API"` and the base URL substring, neither of which was touched.
- `launch.sh` has no test coverage (confirmed via grep). Ran `bash -n launch.sh` (syntax check) plus an isolated invocation of `build_prompt()` (extracted the function, sourced it with dummy `SERVER`/`ROOM`/`TASK`/`ROSTER`/`ROLE_DESCRIPTIONS` values, called it directly) to confirm the rendered prompt text.
- That isolated invocation caught a real bug in the first version of the edit: `launch.sh`'s heredoc is intentionally unquoted (`<<PROMPT`, not `<<'PROMPT'`) so `${SERVER}`/`${ROOM}`/etc. expand — but that also means backticks are live command substitution. The added sentence used `` `since` ``/`` `created_at` `` for markdown-style emphasis, which bash executed as commands (`since: command not found`) and silently dropped from the rendered prompt. Fixed by escaping as `` \`since\` `` / `` \`created_at\` ``; re-ran the same invocation to confirm the literal backticks now render correctly with no shell errors.
