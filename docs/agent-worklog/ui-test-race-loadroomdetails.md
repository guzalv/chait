# UI Test Race in loadRoomDetails

## Changes
- `loadRoomDetails()` in `templates/dashboard.html` now caches the last-rendered `#agents-list`/`#docs-list` HTML and only writes `innerHTML` when the content actually changed.

## Decisions
- Root cause: on page load, the sessionStorage-based room restore (`selectRoom(savedRoom, false)` at the bottom of the script) fires automatically. Since the UI test suite reuses one room across a session-scoped browser, every subsequent `driver.get()` followed by a test clicking the same room row triggers a second, concurrent `selectRoom()` call for the *same* room. Both calls independently `await` and then rewrite `#agents-list` via `loadRoomDetails()`. Whichever resolves last replaces the DOM nodes the other already returned to the test, producing `StaleElementReferenceException` (observed on `.agent-card` text reads and `.dm-btn` clickability checks).
- First attempt: a sequence-token reentrancy guard so only the most-recently-*started* `loadRoomDetails()` call could write. This still failed intermittently in CI (a *different* test, `test_dm_modal_opens_with_agent_name`, also started failing) — because both racing calls fetch the *same* room data, so the "winning" call still performs a redundant `innerHTML` write with identical content, and the outcome depends on completion order relative to Selenium's find+read, not start order. The token only reorders which call wins; it doesn't stop the destructive write from happening.
- Content-diff guard fixes this directly: when the two racing calls' fetched data is identical (the common case — no room state changed in the ~100ms window between them), the second call's write becomes a true no-op, so the DOM nodes Selenium is holding are never touched, regardless of which request resolves first. This also cuts pointless reflows on every `pollMessages()`-triggered `loadRoomDetails()` call when nothing in the room actually changed.
- Considered guarding `selectRoom()` itself with `if(name===currentRoom)return;` to prevent the duplicate call outright. Rejected: `currentRoom` is not reset when using the mobile "back" button (only `showSidebar()` runs, not the `popstate` handler), so re-tapping the same room from the sidebar after going back would silently no-op and leave the user stuck on the sidebar — a real regression with no test coverage to catch it.
- Scoped to `loadRoomDetails()` only, the single choke point all three callers (`selectRoom`, `pollMessages`, `uploadFile`) route through. Doesn't address a similar (currently untested) potential race in `renderMessages`/`appendMessages` if a user switches rooms mid-poll; left as-is since no test exercises it (see `ponytail:` comment in code for the scope of the guard).

## Testing
- Confirmed the failing CI tests reproduced `StaleElementReferenceException` via `gh run view --log-failed` on runs 32676942923 (`test_agent_card_shows_skills`, `test_close_dismisses_modal`) and 32678665548 (`test_dm_modal_opens_with_agent_name`, `test_close_dismisses_modal`, after the first fix attempt).
- `make test` (test-api, test-integration, test-ui — 113 tests) passes.
- Ran `pytest tests/test_ui.py -v` (47 tests) 5x in a row locally after the content-diff fix: all green, no staleness errors. Pushed to CI (PR #3) for final confirmation under CI's slower/more contended timing, where the race reproduces more reliably.
