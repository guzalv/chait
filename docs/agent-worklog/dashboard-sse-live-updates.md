# Dashboard Live Updates via SSE

## Changes
- `server.py`: added `_ui_subscribers` (a `set[asyncio.Queue]`) and `_broadcast_ui(kind)` next to the existing `_unread_events`/`_notify_agent` long-poll plumbing. New `GET /ui/api/events` endpoint (human-session-authed) streams Server-Sent Events: one queue per connected browser tab, a 20s keep-alive comment ping, `Cache-Control: no-cache`.
- `_broadcast_ui(...)` calls added at every state-changing endpoint the dashboard cares about: agent join (`join_with_token`), agent leave (`deregister`, `ui_remove_agent`), room text messages (`post_message`, `ui_send_message`), DMs (`send_dm`, `ui_send_dm`), document uploads (`upload_document`, `ui_upload_document`), room creation (`api_create_room`, `ui_create_room`), and room status changes (`set_room_status`, `ui_set_room_status` — the latter previously had no notification of any kind).
- `templates/dashboard.html`: replaced the four `setInterval` polling loops (rooms every 10s, messages every 3s, DM history every 3s, room-DMs every 3s) with one `EventSource('/ui/api/events')` connection (`connectEvents()`). On every SSE message the browser just re-runs its existing fetch functions (`loadRooms`, `pollMessages`, `loadRoomDetails`, `loadDMHistory`, `loadRoomDMs`) — no per-event-type payload/filtering, since those functions are already cheap no-ops when nothing relevant changed (cursor-based message polling; room/DM/details fetches are scoped by URL to the room/agent already open). Connection health (`Live`/`Disconnected` badge) now comes from `EventSource.onopen`/`onerror` instead of a separate 15s-staleness timer.
- Added content-diff guards to `loadRooms()` and `loadDMHistory()`/`loadRoomDMs()` (same pattern as the existing `loadRoomDetails()` guard from `5e5729f`): skip the `innerHTML` write when the rendered HTML is identical to last time.
- Tests: `test_api.py::TestHumanUI::test_ui_events_requires_session` (auth check); `test_ui.py::TestSSEEndpoint` (`test_requires_login`, `test_delivers_event_on_new_message` — raw HTTP against the real subprocess server, no Selenium). `test_api.py`/`test_integration.py`'s `client` fixtures now also clear `server._ui_subscribers` between tests.

## Decisions
- **SSE over WebSockets or "just poll more"**: the server already has a working per-agent long-poll mechanism (`_unread_events`/`asyncio.Event`, used by agents via `GET /api/v1/me/unread?wait=N`) that the dashboard never used. SSE reuses the same "wake a waiter" shape (one queue instead of one event, since multiple browser tabs can be subscribed at once) without adding a dependency — `StreamingResponse` is already part of FastAPI/Starlette. A prior productification note (`docs/plans/productification/05-remove-unused-deps.md`) explicitly removed an unused `websockets` package; that constraint is about the *agent* protocol ("No SDK, no WebSockets — just curl", `README.md`), not the human browser dashboard, so it doesn't apply here.
- **No per-event payload/filtering**: considered including `{"room": ..., "peer_id": ...}` in each event so the browser could skip irrelevant refreshes. Rejected — every consumer function is already scoped by URL (`/rooms/{currentRoom}/...`, `/dm/{dmTargetId}`) or cheap-when-empty (`pollMessages` with a `since` cursor), so filtering would add code on both ends to save a handful of redundant small GETs in a single-human-dashboard tool. `_broadcast_ui(kind)`'s `kind` argument is kept only as a debug label in the wire payload, not consumed by the frontend.
- **Closing two real gaps found during investigation, not just adding push**: (1) the member panel previously only refreshed via `loadRoomDetails()` piggybacked on `pollMessages()` finding a *new message* (`dashboard.html`, pre-existing) — an agent join/leave with no accompanying message left the panel stale until the room was reopened. Now `loadRoomDetails()` runs on every SSE tick directly. (2) `ui_set_room_status` (agent-facing `set_room_status` too) previously called neither `_notify_room_members` nor anything else — status changes were invisible to both the long-poll agents and the dashboard until the next unrelated poll. Both now broadcast.
- **Diff-guards on `loadRooms`/`loadDMHistory`/`loadRoomDMs`**: SSE fires on *any* connected event system-wide, not just every-3-10s like the old timers, so these functions now run far more often, including for events unrelated to what they render (e.g. a DM to a different agent while the room-DMs modal is open). `tests/test_ui.py` does `find_elements(...)` then iterates/reads/clicks the results for `.room-item` in ~15 places — exactly the pattern that caused the `StaleElementReferenceException` race fixed in `5e5729f` for `.agent-card`. Added the same guard preemptively for `#rooms-list`, `#dm-messages`, `#room-dms-messages` rather than waiting to reproduce the same bug at the new call frequency.
- **No fallback polling safety net**: `EventSource` auto-reconnects natively on drop (browser-managed, no code needed); didn't add a secondary low-frequency poll as a belt-and-suspenders. Add one if reconnect behavior proves unreliable in practice.
- **Out of scope, flagged but not fixed**: found that the already-merged "Room DMs" feature (commit `dd12d3e`, frontend `openRoomDMs`/`loadRoomDMs` calling `GET /ui/api/rooms/{room_name}/dms`) has no corresponding backend route — it 404s every time. Pre-existing, unrelated to this change; `loadRoomDMs()` was still updated for consistency (diff-guard, SSE trigger) since it costs nothing extra and makes the feature work correctly for free once the backend route exists.

## Testing
- `make test-api` (51), `make test-integration` (16), `make test-ui` (49, including the 2 new `TestSSEEndpoint` tests) — all pass. `make lint` clean.
- Manually verified end-to-end against a real subprocess server (not just in-process `TestClient`, which buffers the entire ASGI response and can't drive an infinite SSE stream — confirmed by reproducing a hang): a background thread opens `/ui/api/events`, main thread posts a room message via the agent API, thread receives `data: message` within the 5s join timeout.
- Ran the full 49-test `test_ui.py` Selenium suite (which reuses one session-scoped browser/room across dozens of tests, the exact scenario `5e5729f` was fixed for) 1x clean after the SSE rewrite to confirm the higher event-driven call frequency didn't reintroduce stale-element races.
